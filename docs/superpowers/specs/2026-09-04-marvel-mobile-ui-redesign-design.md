# Marvel Flowchart JP — モバイルUI再設計

作成日: 2026-09-04
状態: レビュー待ち
対象: スマートフォン幅（`max-width: 760px`）の表示・操作層

## 1. 背景と目的

現在のスマートフォンUIは、PC版と同じHTMLをレスポンシブCSS、固定`dvh`、横スクロールタブ、ボトムシートで適応させている。これまでの個別修正で選択・点灯・予習は動作しているが、情報構造そのものはPC前提のままであり、機能追加のたびに「隠す」「縮める」「固定する」例外が増える。

この再設計では、PC画面を縮小したものではなく、スマートフォンでの目的と操作順を起点にしたモバイルシェルを導入する。作品をチャートから眺めて探す流れと、作品を検索して予習する流れを同じ重みで扱い、両方が一つの選択状態を共有する。

## 2. 利用者目標

スマートフォン利用者は次の二つを同じ優先度で実行できることを目標とする。

1. チャートを眺め、作品をタップし、前史・後続・関係を確認する。
2. 作品を検索・絞り込みし、見る順番と視聴済み状態を管理する。

共通して、選択作品・ゴール・点灯状態は画面を移動しても失われない。チャート上の再タップ解除、空白タップ解除、別作品選択の既存契約も維持する。

## 3. 設計原則

- **共通エンジン、別プレゼンテーション**: 作品データ、選択状態、点灯計算、予習計算はPCとスマホで共有する。画面骨格、DOM、ナビゲーション、操作モデルは分離する。
- **目的で分ける**: スマホの主要画面は表示モードではなく「チャート」「探す」「予習」という利用目的で構成する。
- **状態は一つ**: 各画面が個別の選択状態を持たず、共通ストアを唯一の真実とする。
- **必要な画面だけ生成**: `display:none`で三画面を常時保持せず、アクティブ画面をマウントする。チャートのパン・ズーム状態は画面切替で不必要に破棄しない。
- **PCを壊さない**: 当面PCシェルは既存構成を維持し、スマホ幅でのみ新シェルを有効にする。
- **意味論を変えない**: UI再設計では作品間の線、世界線、予習データ、canonical CSVを変更しない。

## 4. アーキテクチャ

### 4.1 共通エンジン

既存処理を一つの状態源として扱い、モバイルシェルからも同じAPIを呼び出す。責務は次の境界を持つ。

- `Repository`: 作品・作品詳細・検索用メタデータの読み取り。
- `SelectionStore`: 現在選択、ゴール、解除、視聴済み状態の保持と購読。
- `HighlightEngine`: 選択から前史・後続・関係線の点灯集合を計算。
- `PlanEngine`: サイト提案ルート、完全版、視聴済み進捗の計算。
- `NavigationState`: 現在のモバイル画面、開いているシート、検索条件、URL/履歴同期。

共通エンジンは既存のグラフ・予習ロジックのラッパーから始め、再設計のために意味論を再実装しない。

### 4.2 モバイルシェル

スマホ幅では次の専用DOMを使用する。PC用`header`、`#left`、`#right`をCSSだけで別用途へ変形させない。

- `MobileAppShell`: safe-area、ビューポート、シート、下部ナビの親。
- `MobileTopBar`: 検索入口、現在のゴール、シート起動ボタン。
- `MobileViewHost`: アクティブな一画面だけをマウントする領域。
- `MobileBottomNav`: 「チャート」「探す」「予習」の3項目。
- `MobileSheetController`: 詳細、接続理由、表示設定を一つのシート内で切り替える。

作品カード、作品名、日付、バッジなどの表示部品は、必要なら共通rendererを使う。ただし、PCのパネルDOMをそのまま再利用することはしない。

## 5. 画面設計

### 5.1 チャート

目的は「世界を眺め、作品を選ぶ」こと。

- 画面の大部分をチャートに割り当てる。
- 上部には検索への入口、現在のゴールチップ、解除ボタンだけを置く。
- 1本指パン、2本指ズーム、作品タップ、空白タップ解除を維持する。
- 表示ビュー切替（関係地図、公開順、世界線・時系列など）はフローティングボタンからシートで行う。
- 作品タップ後、詳細を自動的に画面全体へ遷移させず、必要時に共通シートを開ける。
- 既存Canvas/SVGの点灯計算と座標系を使い、シート開閉ではチャートを再生成しない。

### 5.2 探す

目的は「作品を見つけ、チャートまたは予習へ送る」こと。

- 画面上部に常時フォーカス可能な検索欄を置く。
- MCU、X-MEN、Spider-Man、公開順、作品種別など、既存の検索・絞り込み条件を段階的に移す。
- 作品カードの主操作は「選択」。副操作で「チャートで見る」「詳細」を提供する。
- 選択後にチャートへ移動しても、選択作品・ゴール・点灯状態を共通ストアから復元する。
- 131作品程度の現行規模では通常リスト描画とし、仮想化は計測で必要になった場合だけ導入する。

### 5.3 予習

目的は「何を見るかを決め、進捗を管理する」こと。

- 現在のゴール、対象作品、予習順、視聴済みチェックを表示する。
- 公開UIとしてはサイト提案ルートと完全版を中心にし、データとして残る公式ルートを独立ボタンとして再導入しない。
- 予習リストの作品タップは詳細シートを開き、チャートボタンでチャートへ戻れるようにする。
- 予習済みの変更は共通ストアへ即時反映し、チャートへ戻ったときの点灯・表示状態と矛盾させない。

## 6. シートとナビゲーション

### 6.1 単一シート制御

詳細・接続理由・表示設定を別々の固定パネルとして重ねず、一つの`MobileSheetController`が内容を切り替える。シートの状態は `closed | detail | reason | settings` のいずれか一つとする。

シートは次のアクセシビリティ契約を持つ。

- `aria-modal="true"` と適切なlabelを付ける。
- 開いたときに先頭の見出しまたは閉じるボタンへフォーカスする。
- 閉じたときに起点のボタンまたは作品カードへフォーカスを戻す。
- Escape、背景タップ、明示的な閉じる操作で閉じる。
- ブラウザの戻る操作は、シートを先に閉じ、次に画面履歴を戻す。

### 6.2 下部ナビ

下部ナビは常時表示するが、シートが開いている間は操作対象をシートへ限定する。現在画面は色だけでなく`aria-current`でも示す。safe-area insetを含め、44px以上のタッチ領域を確保する。

## 7. URL・履歴・ディープリンク

画面を変えても状態が曖昧にならないよう、次の状態をURLまたは履歴エントリへ同期する。

- 現在画面（チャート／探す／予習）。
- 選択またはゴールの作品ID。
- 開いているシート種別と対象作品ID。
- 検索語・主要な絞り込み条件。

新規モバイル状態は、既存の共有リンクを壊さないよう次のクエリキーで表現する。`mview=chart|search|plan`、複数ゴールをカンマ区切りで持つ`goals=<work-id,...>`、`sheet=detail|reason|settings`、対象を示す`sheetWork=<work-id>`、検索語を示す`q=<text>`を使用する。絞り込み条件は既存キーと衝突しない`mfilter=<encoded-filter>`へまとめ、未指定は既定値とする。既存の`#room=...`などの共有用ハッシュは保持し、未知のキーは無視する。検索から、チャートから、予習から同じ作品を開いた場合は同じ作品状態へ到達する。ブラウザの戻る操作で、シートを閉じる → 画面を戻す → 直前のゴール状態を戻す、という順序を固定する。

## 8. パフォーマンス

- 非アクティブ画面のリスト・詳細DOMを常時生成しない。
- チャートrendererは画面切替で破棄せず、必要なときだけ点灯レイヤーを更新する。
- 検索入力では毎キーごとの重いSVG再生成を避け、結果リストだけを更新する。
- シートの開閉はチャートのCanvas/SVG再生成を起こさない。
- 初回表示、シート開閉、検索、パン・ズームの不要な再描画をブラウザ監査で計測する。
- Pixel 6相当の縦長画面と標準Android幅を最低限の性能対象にする。

## 9. 段階的な移行

### Phase M1: 共通状態境界

現在の選択・点灯・予習処理を`SelectionStore`、`HighlightEngine`、`PlanEngine`から購読できる形に整理する。見た目は変更しない。既存のPC・ブラウザ監査を全て通す。

### Phase M2: モバイルシェル骨格

モバイル幅だけ新しいシェルを表示し、3画面の切替、単一シート、safe-area、戻る操作を実装する。画面内容は暫定でよいが、状態同期とナビゲーション契約を固定する。

### Phase M3: チャート面の移行

チャートの表示領域とタッチ操作を新シェルへ移す。再タップ解除、背景解除、ドラッグ後の選択維持、ビュー切替後の点灯維持を回帰テストする。

### Phase M4: 探す面の移行

検索・絞り込み・作品カードを新シェルへ移し、検索 → チャート、検索 → 予習の導線を追加する。

### Phase M5: 予習面の移行

サイト提案ルート、完全版、視聴済みチェック、チャート復帰を新シェルへ移す。公式ルートのデータ保持と公開UI非表示を維持する。

### Phase M6: 旧モバイル層の撤去

全回帰が通った後、旧モバイル用の固定配置・重複シート・不要な例外CSSを削除する。PCシェルと共通エンジンは維持する。

## 10. テスト計画

### 10.1 ユニット／契約

- 3画面間で選択作品・ゴール・視聴済み状態が一致する。
- 画面切替やシート開閉でチャート座標・ズームが変わらない。
- 戻る操作の順序がシート → 画面 → ゴール履歴になる。
- 非アクティブ画面が不要な重いrendererを生成しない。
- 既存の点灯集合、予習順、作品ID、エッジIDが変わらない。

### 10.2 実ブラウザ操作

最低限、Chrome/CDPで次を実操作として監査する。

- チャート上の選択、再タップ解除、背景タップ解除。
- チャートのパン・ズーム後の選択維持。
- 探す → 選択 → チャートで見る。
- 予習 → 詳細シート → チャート復帰。
- シートのEscape・背景タップ・戻る操作。
- 縦長iPhone相当、Pixel 6相当、横向きの表示崩れ。

### 10.3 既存回帰

モバイルUIの変更後も、既存の全ユニットテスト、ビルド、選択監査、操作監査、時系列監査、公開順監査を実行する。canonical CSV、グラフのエッジ、予習データは差分ゼロであることを確認する。

## 11. 非対象

- PC版の画面骨格を今回同時に刷新しない。
- canonical CSV、作品間の線、世界線・時系列の意味論を変更しない。
- ネイティブアプリ化、ログイン、サーバー側状態保存を導入しない。
- 公式予習ルートのデータを削除しない。

## 12. 受け入れ基準

次を全て満たしたとき、モバイルUI再設計を完了とする。

1. チャート・探す・予習の3面を下部ナビで切り替えられる。
2. どの面から作品を選んでも、共通の選択・ゴール・点灯状態になる。
3. チャートのパン・ズーム・解除操作が既存契約どおり動く。
4. 詳細・接続理由・設定は単一シートで扱われ、戻る操作が予測可能である。
5. URL／履歴から作品と画面を再現できる。
6. 非アクティブ画面の不要な重いDOM・rendererを生成しない。
7. PC版、canonical data、グラフ意味論に回帰がない。
8. 実機相当の縦長・横向き画面で文字被り、タッチ領域不足、スクロール不能がない。
